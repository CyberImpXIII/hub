## 3. Design findings

1. **`hub check` fails on day one as written.** §2's example declares `"task": null`,
   and §8's vocabulary gate rejects a `null` tag at a node where no child advertises
   it; children register in H3, so from H1a to H3 the root's own registry fails its own
   check. Either an explicitly addressed envelope (`--to node/role`) needs no tag route
   and the gate says so, or `task` routes to the role whose `dir` the `ref` names. Say
   which.
2. **`hub log --cost` reports USD; cost here is tokens.** The `result` line's
   `total_cost_usd` is list price, not what a Max plan pays. Log the `result` line's
   `usage` tokens per spawn and show them in units of 1u; keep `--max-budget-usd` as a
   kill switch only.
3. **Admission needs a fourth check.** PLAN-usage-reporting.md §3, written after the
   brief: before a `task` envelope spawns, the server asks `usage gate <estimate>`;
   `warn` holds only checkpointable jobs, `hold` queues and tells Jacob once. Add it to
   §3's admission list and to §8's admission row. It is the hub rule the usage plan
   proposed as brief §4 item 11.
4. **A server spawn must carry the commit stamp.** PLAN-hard-gates.md §2 stamps commits
   with `agent_type` from the hook input; a cold role started with `--agent <role>`
   carries it, so the hub changes nothing, but "a commit from a server-spawned role
   carries `Agent: <role>`" belongs in §8's conformance row.
5. **H1a is one 250-400k job with a harness half.** PLAN-check-progress.md §7 exists
   because jobs die at usage limits. Split it: H1a-1 (schema, `init|check|up|down|status`,
   `/health`, the kill-the-server and registry gates) and H1a-2 (the moved parser,
   origin, `/route`, `/sessions`, admission, the relay through the server, the harness
   half). Each under 200k, each leaving the system working.
6. **W1's restart is the wrong command** (§2 above). Replace with stop and start; the
   probe stands.
7. **§11 is a second plan inside the first.** Same repo, same CLI (Decision 9 holds),
   but its own file, `PLAN-hub-view.md`, carrying the V phases, the Wave probe and its
   own Decisions (the plan's 1, 2, 9, 11, 12), so the hub's merge and build do not wait
   on a terminal-host choice that rests on a probe nobody has run (Risks says so).
8. **The build phases are cloud-eligible.** H1a, S1, H1b, H2 and H3 are Node code with
   fixture repos and offline tests, public-safe inputs, a branch as output:
   PLAN-cloud-offload.md §3's predicate holds. H0 (probes on this machine), V1-V3 (the
   terminal), H4 (the dispatcher's prose) and H5 (measurement) are local. While the
   credits last, "each phase is one `deep-work` job" should read "one cloud session
   Jacob starts, by PLAN-cloud-offload.md §8's procedure, for the eligible phases".
9. **Reports owed** (the plan's Risks, next-to-last bullet) go out after Jacob's yes,
   not before: cron-scheduler (`chron.py list --json`; the server list from `hub status
   --json --tree`); harness (`gen` renders `hub.json`, three hooks become `hub hook`
   callers, the guard reads `hub status`, `quote-words.sh` reads `hub origin`);
   tools/setup (the `hub` component, `.gitignore` lines); tools/checks (`hub sync --check
   --json` after S1). Recorded in TODO.md so each is sent once.
